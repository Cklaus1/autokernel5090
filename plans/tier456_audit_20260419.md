### T4.1 — Launch-script env-var systematic scan — **RECOVER (multi-script hygiene bug)**

**Current state.** 10 top-level `launch_*.sh`. `launch_qwen3_fused_norm_fp4.sh` does set `VLLM_USE_FLASHINFER_MOE_FP4=0` (line 93) and `launch_qwen3_fused_t2n.sh` also sets it (line 72) — the original thesis "missing from launch_qwen3_fused_norm_fp4.sh" is incorrect as of the file on disk. They also all propagate the WSL2 `--gpus 'device=N'` + `-e CUDA_VISIBLE_DEVICES=0` pattern — correct on WSL2 per 2026-04-18 doc, but 2 scripts (`launch_v1_graph.sh`, `launch_v1_nograph.sh`) export `CUDA_VISIBLE_DEVICES=1` WITHOUT any `--gpus` pairing (they run on host sglang venv, not Docker), which on WSL2 is a silent no-op (both GPUs visible to the host Python process regardless).

**Smoking-gun checks.**
- `launch_qwen3_fused_norm_fp4.sh:15`, `launch_qwen3_fused_t2n.sh:15`, `launch_gemma4_swa.sh`, `launch_gemma4_swa_fp8.sh`, `launch_prefix_aware_sched.sh`, `launch_gemma4_lmcache_hierarchy.sh`, `launch_lmcache_smoke_sm120.sh` — all seven have `NAME="${NAME:-vllm-...-${MODE}}"` with NO defensive `unset NAME`. Single `CUDA_VISIBLE_DEVICES` set from a WSL2 host-shell is still respected inside the same Python process, so this is probably fine — but there's no UUID check.
- `launch_qwen3_fused_norm_fp4.sh:41-42` and `launch_qwen3_fused_t2n.sh:42-43` both pass `-cc.mode none -cc.cudagraph_mode full` as two separate vLLM-args entries. vLLM's arg parser DOES accept this form. `launch_prefix_aware_sched.sh:38-39` same. `launch_gemma4_lmcache_hierarchy.sh:75-76` same. **Verdict: RECOVER.** One defensive `unset NAME` at the top of each script (8 lines across 8 files) closes a cross-experiment container-name collision hole. Impact: **prevents silent container clobber across 8 experiments**.

**Fix (8 lines):**
```bash

```

Apply to: `launch_qwen3_fused_norm_fp4.sh`, `launch_qwen3_fused_t2n.sh`, `launch_gemma4_swa.sh`, `launch_gemma4_swa_fp8.sh`, `launch_prefix_aware_sched.sh`, `launch_gemma4_lmcache_hierarchy.sh`, `launch_lmcache_smoke_sm120.sh`, `launch_lmcache_remote.sh`.

### T4.4 — WSL2 GPU isolation durable workaround — **RECOVER (template docker run)**

**Current state.** `experiment_log_20260418.md` §Insight #2 and #10: `docker --gpus 'device=N'` does NOT isolate on WSL2; both containers see both GPUs unless `CUDA_VISIBLE_DEVICES=N` is ALSO set on the container env. All current `launch_*.sh` correctly combine both, EXCEPT `launch_lmcache_smoke_sm120.sh:24-26` which sets `--gpus 'device=0'` + `-e CUDA_VISIBLE_DEVICES=0` — fine by current rule, but has no UUID verification.

**Smoking-gun checks.**
- The isolation combination is: `--gpus 'device=N'` (host-side gpu pass) + `-e CUDA_VISIBLE_DEVICES=0` (container sees one device, renumbered to 0) + optionally `-e NVIDIA_VISIBLE_DEVICES=N` (NVIDIA container runtime ordinal filter). Current scripts only use the first two.
- `NVIDIA_VISIBLE_DEVICES=N` at `docker run` does NOT help on WSL2 because the NVIDIA runtime's WSL2 shim maps all GPUs regardless. Adding it is net-zero (harmless, no benefit).
- Cgroup-based isolation (`--cgroup-parent`, `--device /dev/nvidia0`) does NOT work on WSL2 because WSL2 doesn't expose `/dev/nvidia*` — they're virtualized via `/dev/dxg`.
- The one durable trick missing is: **UUID assertion inside the container**. `torch.cuda.get_device_properties(0).uuid` check as the first line of every vLLM bench.

**Verdict: RECOVER.** No "better" docker-run invocation exists on WSL2 (isolation is fundamentally a WSL2 limitation). But a UUID-assertion boot check will catch leaks in every future experiment.

**Fix (template add to all launch scripts' INNER_SCRIPT):**
```bash
python3 -c "import torch; u=torch.cuda.get_device_properties(0).uuid; print(f'[GPU_CHECK] dev0 uuid={u}', flush=True)" || exit 1
```

Drop this as first line of each INNER_SCRIPT (after `set -e`). Correlate with host `nvidia-smi -q | grep UUID` to verify correct GPU pinning.
